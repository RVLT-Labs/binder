All settings writes in the web now go through one helper that reads and writes inside a single PowerSync write transaction.

## Rulings made while executing (each with what it costs if wrong)

19. The stagger between parallel connectors on one line and side is computed pairwise in placement order: `offset_i = offset_prev + max(LEADER_STEP, (w_prev + w_i) / 2 + 0.75)`, the first connector having offset 0. For equal widths this is exactly the plan's `max(LEADER_STEP, w + 0.75)`, and for thin it is exactly today's 1.5 pt, so existing shows are unchanged. Two departments with different widths on one line is normal (LX and SND), and the plan only stated the single-width case. Cost: mixed-width connectors sit slightly closer or further apart. (Spec sentence added in the Phase 3 docs commit.)
20. The Phase 3 e2e checks the connector style on the page (SVG stroke attributes) and in the EXPORTED PDF's content stream (`2.5 w`, `[10 6.25] 0 d`), not in the Print dialog preview, because that preview draws only margin tags, never cues.
21. Heavy staggered connectors may touch the next line: the second bold connector on a crowded line sits about 3.25 pt under the underline. The spec's own formula causes this. The docs are softened ("a thin connector never crosses a glyph; heavier ones staggered under a crowded line can touch the line below") rather than the geometry changed. **Raise with Jayden as a known limit.** Cost: a heavy connector can touch the line below on a crowded line.
22. The `Segmented` control is 27 px tall from the `md` breakpoint up with no coarse-pointer override, so on an iPad the new radios (and Marker side and Number format, which share the control) are under the 44 px target. This is pre-existing and a global change to a shared primitive, so it was left alone and flagged. Cost: small touch targets on the settings page on an iPad.
23. Print strokes a dashed or dotted jogged connector segment by segment, so the pattern restarts at each corner and a bold dashed corner can show a small notch (the screenshots look slightly blocky). The spec accepts the restart and solid connectors keep their old bytes, so a single-path stroke for dashed and dotted jogs was not done. Cost: slightly blocky dashed corners in print.
24. On a phone card the Hidden checkbox comes before the connector controls in the DOM but still appears below them (`max-md:order-1` and `max-md:order-2`), so keyboard tab order matches the visual order from `md` up and differs on a phone. Dropping the order classes would put Hidden above the connector controls on phones. Cost: phone keyboard tab order visits Hidden before the connector controls.

## Deferred minors (reviewers raised them; none blocks merge)

- Task 16: with all-thin leaders whose targets are 2 pt apart (the "same line" window of 3 pt is not transitive) the offsets can be 0 / 1.5 / 3 instead of the old 0 / 1.5 / 1.5 (no collision, arguably better; pin with a test or leave); solid is drawn with round caps in print while the layout says `round: false` (comment and test title at `cueTags.test.ts:141` should say so); `CONNECTOR_WEIGHT[style.width] ?? LEADER_WIDTH` is only safe for typed input (unreachable); no standalone RED for the `stampItems` test.
- Task 17: `useConnectorStyles` and `useMarkerSides` (and the width and pattern controls) are near duplicates; the visible "Connector width" label is a plain `div` not tied to its radiogroup (the group's `aria-label` covers it).
- Whole phase: thin dotted (0.75 pt dots, 1.875 pt gap) may read as a faint grey line on a photocopy (inherent to the choice); dotted lines on screen were checked in Chromium only, and the product is iPad and Safari first. The technique (a zero-length dash with round caps) is standard and print is generated by pdf-lib, but **one manual look at dotted connectors on iPad Safari is worth doing before relying on them**.
- Declined by the reviewers as pre-existing: last-writer-wins on the whole `settings` object across devices and through MCP `update_show`; an archived show's owner still sees editable controls (the server refuses the write); `parseSettings` turning corrupt settings text into `{}`.
